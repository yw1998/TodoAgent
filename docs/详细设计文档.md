## 1. 总体架构

```

                                   │      ┌───────────┼───────────┼──┐   │
                                   │      │ LLM Client│ Scheduler │    │  │
                                   │      └─────┬─────┴─────┬─────┘    │  │
                                   └────────────┼───────────┼──────────┘
                                                ▼           ▼

                                        │   SQLite / PostgreSQL   │
```

### 1.1 模块划分

| 模块 | 职责 |
|------|------|
| `channels/` | 消息渠道抽象与飞书实现：事件回调验签、消息解析、发送消息/卡片 |
| `agent/` | 核心业务：组装 Prompt、调用 LLM、执行 Tool Calling、生成回复 |
| `services/` | 待办 CRUD、配置管理业务逻辑（v2 已移除用户管理） |
| `scheduler/` | APScheduler 封装：注册/取消 job、到期触发提醒、失败重试 |
| `api/` | FastAPI 路由：飞书回调 webhook、管理后台 REST API |
| `web/` | 管理页面（Jinja2 模板 + HTMX，或纯前端调用 REST API） |
| `db/` | SQLAlchemy 模型、Alembic 迁移 |
| `llm/` | LLM 客户端封装（OpenAI 兼容协议，可配置 base_url/model） |

## 3. 数据模型设计

### 3.1 ER 概览

```
todos 1──N reminder_logs
settings (key-value 全局配置，含通知目标 feishu_notify_open_id/chat_id)
message_logs / admins（v2 单人化：已删除 users 表与各表 user_id 列，启动时自动迁移存量库）
```

### 3.2 表结构

**通知目标**（替代原 users 表，存于 settings）

| 键 | 说明 |
|------|------|
| feishu_notify_open_id | 最后来消息用户的 open_id |
| feishu_notify_chat_id | 最后来消息会话的 chat_id（oc_ 前缀优先用于发送） |

**todos**

| 字段 | 类型 | 说明 |
|------|------|------|
| id | INT PK | |
| title | VARCHAR(255) | 待办标题 |
| note | TEXT | 备注，可空 |
| next_remind_at | DATETIME | 下次提醒时间（UTC 存储） |
| repeat_rule | VARCHAR(64) | 可空；cron 表达式或 RRULE，如 `0 10 * * 1` |
| status | VARCHAR(16) | `pending` / `overdue` / `done` / `cancelled` |
| source_message | TEXT | 触发创建的原始消息 |
| remind_count | INT | 已提醒次数 |
| snooze_until | DATETIME | 可空；延后提醒时间 |
| created_at / updated_at / done_at | DATETIME | |

索引：`(status, next_remind_at)`（调度扫描）。

**settings**（管理页配置，敏感值加密）

| 字段 | 类型 | 说明 |
|------|------|------|
| key | VARCHAR(64) PK | 如 `llm.api_key`、`feishu.app_secret` |
| value | TEXT | AES-GCM 加密后存储（is_secret 项） |
| is_secret | BOOL | 页面展示时脱敏为 `***` |
| updated_at | DATETIME | |

预置 key：`llm.base_url` / `llm.api_key` / `llm.model` / `llm.temperature` / `llm.timeout` / `feishu.app_id` / `feishu.app_secret` / `feishu.verification_token` / `feishu.encrypt_key` / `scheduler.timezone` / `scheduler.tick_seconds` / `scheduler.max_retry`。

**message_logs**

| 字段 | 类型 | 说明 |
|------|------|------|
| id | INT PK | |
| direction | VARCHAR(8) | `in` / `out` |
| content | TEXT | 消息内容 |
| tool_calls | JSON | LLM 返回的工具调用与参数 |
| status | VARCHAR(16) | `ok` / `error` |
| error | TEXT | 失败原因 |
| latency_ms | INT | LLM 调用耗时 |
| created_at | DATETIME | |

**reminder_logs**：`id, todo_id FK, fired_at, status, error`，记录每次提醒发送结果。

**admins**：`id, username, password_hash(bcrypt), created_at`，管理页登录用。初始账号由环境变量 `ADMIN_INIT_USERNAME/PASSWORD` 首次启动创建。

## 4. 核心流程设计

### 4.1 消息处理主流程

```
飞书事件回调 → webhook 路由
  1. URL 挑战验证 / 签名校验（verification token + 可选 encrypt_key AES 解密）
  2. 事件去重：event_id 内存 LRU（保留 5 分钟），重复直接返回 200
  3. 解析消息：仅处理 im.message.receive_v1 且 msg_type=text
  4. 快速 ACK 200（飞书要求 3s 内响应），实际处理投递到 asyncio.Queue，
     由后台 worker 消费（并发度可配，默认 4）
  5. worker：
     a. 更新通知目标（open_id/chat_id → settings）
     b. 写 message_log(in)
     c. AgentService.handle(user, text)
     d. 回复发送回飞书，写 message_log(out)
```

### 4.2 Agent Service（Tool Calling 循环）

```python
async def handle(user, text) -> str:
    messages = load_context(user.id)            # 最近 N=10 轮，存内存/DB
    messages.append(user_msg(text))             # 附带系统时间上下文
    for _ in range(MAX_TOOL_ROUNDS):            # 默认 4
        resp = await llm.chat(messages, tools=TOOL_SCHEMAS)
        if not resp.tool_calls:
            break
        for tc in resp.tool_calls:
            result = TOOL_HANDLERS[tc.name](user, tc.args)   # 执行 DB 操作/调度注册
            messages.append(tool_result(tc.id, result))
    save_context(user.id, messages)
    return resp.content
```

**Tool schema 要点**：

- `create_todo(title: str, remind_at: str /*ISO8601*/, repeat_cron?: str, note?: str)`
  - handler 校验 `remind_at` 晚于当前时间；创建 todo → 调用 scheduler 注册 job → 返回 `{todo_id, formatted_time}` 供 LLM 组织确认文案。
- `list_todos(status?: "pending"|"done"|"all", from?: str, to?: str)` — 返回结构化列表，LLM 生成自然语言摘要。
- `update_todo(todo_id, title?, remind_at?, repeat_cron?)` — 更新后必须重注册调度 job。
- `complete_todo(todo_id)` / `delete_todo(todo_id)` — 移除调度 job。
- 待办 id 消歧：LLM 上下文注入该用户 pending 待办的 `id+title` 摘要（token 开销小），"把买菜的提醒改到下午3点" 可由 LLM 匹配到 id；无法唯一确定时 LLM 追问。

### 4.3 提醒调度设计

采用 **DB 轮询 + APScheduler** 混合方案，兼顾简单与可靠：

- APScheduler `AsyncIOScheduler`，SQLAlchemyJobStore 持久化 job，服务重启后 job 恢复。
- 每条 pending todo 对应一个 `date` job（`next_remind_at` 触发）；周期 todo 触发后按 `repeat_rule`(cron) 计算并注册下一次。
- **兜底扫描**：每 `tick_seconds`(默认 30s) 执行 `SELECT * FROM todos WHERE status='pending' AND next_remind_at <= now()`，捕获 jobstore 丢失/服务宕机期间错过的提醒，防漏防重（用 `remind_count` + 条件 UPDATE 抢占）。
- 提醒触发流程：发送飞书消息（卡片：标题+时间+「完成/延后」按钮说明）→ 写 reminder_log → 失败按 2s/8s/32s 重试 3 次 → 更新 `next_remind_at`（周期）或置 `done`（一次性可选：默认保持 pending 等用户确认，超过 N 次提醒自动 done，可配置）。

### 4.4 延后（snooze）与确认

用户在提醒后回复"完成/收到/延后10分钟"：消息进入正常 Agent 流程，system prompt 指引 LLM 将此类短句关联到最近一次提醒的 todo，调用 `complete_todo` 或 `update_todo(remind_at=now+10min)`。

## 5. API 设计

### 5.1 Webhook

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/feishu/events` | 事件订阅回调；处理 url_verification 挑战与消息事件 |
| GET | `/healthz` | 存活探针 |

### 5.2 管理后台 REST API（前缀 `/api/admin`，JWT 鉴权）

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/login` | 账号密码 → JWT（24h） |
| GET | `/todos` | 列表；query: `status, q, from, to, page, size` |
| GET | `/todos/{id}` | 详情 + reminder_logs |
| PATCH | `/todos/{id}` | 手动修改（同步重注册 job） |
| DELETE | `/todos/{id}` | 软删除 → cancelled |
| GET/PUT | `/settings` | 配置读取（secret 脱敏）/ 批量更新，热生效 |
| GET | `/message-logs` | 消息日志查询 |

### 5.3 管理页面（Jinja2 + HTMX）

| 路径 | 功能 |
|------|------|
| `/admin/login` | 登录 |
| `/admin/todos` | 待办浏览：过滤表格、状态徽标、手动完成/取消、分页 |
| `/admin/settings` | 配置分组表单（LLM/飞书/调度），保存即热生效 |
| `/admin/logs` | 消息/提醒日志 |

## 6. 关键接口示例

### 6.1 飞书调用

- 发消息：`POST /open-apis/im/v1/messages?receive_id_type=open_id`，header 带 `tenant_access_token`（缓存，过期前 5 分钟刷新）。
- 事件：`im.message.receive_v1`，字段 `sender.sender_id.open_id`、`message.content`（JSON 字符串，`{"text": "..."}`）。

### 6.2 LLM 调用（OpenAI 兼容）

```python
resp = await client.chat.completions.create(
    model=cfg.llm_model,
    messages=[{"role":"system","content": SYSTEM_PROMPT.format(
                 now="2026-10-16 13:00 (UTC+8, 周五)",
                 pending_todos=...)},
              *history, {"role":"user","content":text}],
    tools=TOOL_SCHEMAS, tool_choice="auto",
)
```

System prompt 要求：时间一律输出带时区的 ISO 8601；不确定信息必须追问不猜测；工具执行后用简洁中文确认。

## 7. 配置加载与热生效

优先级：DB `settings` 表 > 环境变量 > `.env` 默认值（pydantic-settings 兜底）。`SettingService` 内存缓存 + 版本号，管理页保存后 bump 版本，Agent/Scheduler 每次使用时按版本重载，实现热生效。敏感项用 `SECRET_KEY` 环境变量派生密钥做 AES-GCM 加密。

## 8. 安全设计

- Webhook 校验飞书 `X-Lark-Signature` / verification token，拒绝伪造事件。
- 管理 API 全部 JWT + 密码 bcrypt；配置读取接口永不明文返回 secret。
- v2 单人部署：已移除多用户归属校验；LLM 工具直接操作唯一用户的待办。
- SQL 全部经 ORM 参数化；页面模板自动转义防 XSS。

## 9. 部署设计

```
docker-compose:
  web:   uvicorn app.main:app --host 0.0.0.0 --port 8000
         (FastAPI 内含 webhook + 管理页 + Agent worker)
  # 数据库默认 SQLite，数据文件挂 volume 即可：./data/todoagent.db
  # 如需迁移 PostgreSQL：设置 DATABASE_URL=postgresql+asyncpg://...
```

- 飞书后台配置：事件订阅 URL 指向 `https://<域名>/feishu/events`，开启 `im.message.receive_v1`，机器人能力开启单聊/群聊。
- 多副本注意：单副本即可满足个人场景；多副本时调度兜底扫描需加分布式锁（`UPDATE ... WHERE next_remind_at<=now` 条件抢占已天然防重）。

## 11. 里程碑规划

1. **M1 基础链路**（1~2 周）：飞书收发 + LLM create_todo/list_todo + SQLite + 一次性提醒调度。
2. **M2 完整待办**：update/complete/delete、周期提醒、snooze、多轮上下文。
3. **M3 管理后台**：登录、配置热生效、待办浏览、消息日志。
4. **M4 加固**：重试/去重/加密、测试覆盖、Docker 部署。

## 12. 扩展点

- 新渠道：实现 `Channel` 接口（事件解析、消息发送）即可接入企业微信/Telegram。
- 多 LLM 供应商：`llm/client.py` 保持 OpenAI 兼容层，改 base_url 即切换。
- 后续可选：语音消息（ASR）、日历联动、Webhook 通知其他系统。
